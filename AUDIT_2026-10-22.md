## 1. Current-state summary

The picture is substantially better than Oct 2. All 13 beta-test UI blockers are fixed except group-chat reachability (partial — superseded by Spaces). The Sept-24 security fixes are intact (Keychain-only tokens, gateway auth, hardened dynamic-script execution). The Oct-2 headline defects — fake meeting quorum, dispatch_swarm false checkmarks, GroupChatSession wiping 1:1 history, turn pollution, dropped bot attachments, dead bot-to-bot @mentions, SpaceManager concurrency races, DynamicToolbox `zsh -c` — are FIXED in code. The gateway unauthenticated-broadcast leak flagged in the Oct 22 security note is also FIXED (broadcasts now filter to authenticated connections; remote confirmations have a 60s fail-closed timeout), so that part of the note is stale.

The center of gravity has moved: the risk map is now complete (78 registered tools, 78 classified), **but the live confirmation gate was never wired to it** (new finding C-1, HIGH). The Oct-2 P0 confirmation cluster is therefore best described as PARTIAL: the direct-fire shims and ask_bot/dispatch_swarm routing are fixed, Path B and the nested-depth leak are mitigated but not closed, and ~20 `.high`-classified tools receive no confirmation prompt by default because `shouldConfirmTool` checks only a hardcoded 5-tool set.

**Tally — 60 prior-finding items re-checked: 36 FIXED · 17 PARTIAL · 3 STILL OPEN · 3 VERIFIED as documented · 1 judged FALSE (docs' own test counts).** Two further still-open items are nested inside partials (InspectAgentStatusIntent's fabricated status; MCPServerProtocol's zero conformers, by design).

## 3. New findings (not in any prior audit)

### Security core

- **C-1 [HIGH] The live confirmation gate ignores the risk map.** `ToolDispatchEngine.swift:11-24`: `dangerousToolNames` = {run_shell_command, delete_file, write_file, run_applescript, create_skill}; `shouldConfirmTool` returns only `requireConfirmationForAll || dangerousToolNames.contains(name)`. AgentOrchestrator delegates to it; executeWithLogging uses it. `AgentSecurity.requiresConfirmation` (.high) is consulted on neither live path in the files read. Consequence: ~20 tools classified .high get NO confirmation by default — execute_dynamic_tool, computer_use, github, discord_bot, discord_webhook, manage_sandbox, simctl, mail_automation, deep_link, control_app, control_accessibility, control_browser, patch_file, calendar, reminders, run_shortcut (delete_file/write_file/create_skill are covered only coincidentally, via the 5-name set). Oct-20 governance work completed the map; the gate was never wired to it.
- **C-2 [MEDIUM] Non-wrapping tools bypass executeWithLogging on every path.** CaptureWindowImageTool, AccessibilityOmniTargeter, DifferentialScreenPerception implement call() with no executeWithLogging — no repeat check, disabled-mode check, call cap, truncation, sanitization, or audit record, regardless of entry path.
- **C-3 [MEDIUM] Collab token accepted in URL query string** (`CollaborativeServer.swift:~227-232, ~381`) — leaks into logs/browser history; same pattern as the Space invite URL (M-4).
- **C-4 [LOW] Gateway accept-time loopback check is string-based** (exact "::1", "127." prefix, "localhost") — fail-closed, so the risk is false rejects, not false accepts.
- **C-5 [LOW] confirmationDepth setter is non-idempotent** (`AgentOrchestrator.swift:258-261`): setting confirmationPerformed=true increments, =false decrements; a stray double-set skews the counter that gates the Area-2 #1 leak.

### Multi-agent

- **M-1 [MEDIUM] Debate coordinator ignores maxRounds.** `MultiAgentDebateCoordinator.conductDebate(...maxRounds:)` never references the parameter — always exactly one round + synthesis. (The pollution half of the Oct-2 debate finding is fixed via executeIsolatedTurn.)
- **M-2 [MEDIUM] BotSession.makeSession force-unwraps the weak orchestrator** (`orchestrator!` twice). If the orchestrator is deallocated, session creation/reset crashes; GroupChat and BotManager mask the same wiring failure by silently substituting a throwaway AgentOrchestrator().
- **M-3 [LOW] ConveneMeeting transcript still lands in the orchestrator chat** (`ConveneMeetingTool.swift:91` appendMessage) rather than a meeting-scoped surface; createVisualSession (`:218`) has no caller in its file.
- **M-4 [MEDIUM, Oct-2 #18 still open] Space invite URL embeds the collab token in the query string** (`SpaceManager.swift:500` inviteURL; also exported in every spaces snapshot).
- **M-5 [LOW] dispatch_swarm empty output still renders ✅** (`DispatchSwarmTool.swift:224` → "Completed with no output." passes isSuccess at `:251`; same for the registry-agent path).
- **M-6 [LOW] Peer-approval expiry is view-driven** (60s poll only while a BotChatView lives, or the next peerDeliveryDecision); "Always Allow" grants are in-memory only and don't survive restart.
- **M-7 [LOW] GroupChat restart hygiene:** runParticipantTurn calls resetSession() on the isolated session every turn (tool/session continuity lost), and start() doesn't clear messages or the mention-mutated generationOrder — a restarted group inherits the previous round's queue.
- **M-8 [INFO] GroupChat tool execution still calls orch.executeToolByName directly** in both .allowed and .needsApproval branches — inherits whatever Path B does (Area-2 #2 / C-2).

### Data & managers

- **D-1 [MEDIUM-LOW] Keychain in-memory fallback masks Keychain failure.** save() populates FallbackStorage unconditionally, even when the Keychain write failed; get() checks the fallback FIRST. Within a session, a failed write looks successful to readers (only the save() Bool/audit log reveal it), and a stale fallback shadows newer Keychain values from other processes.
- **D-2 [MEDIUM] SkillManager.syncFromDisk() prunes the skills it claims to preserve.** diskNames excludes *_procedural files, but the prune loop deletes EVERY persisted Skill whose name ∉ diskNames, contradicting its own "preserve procedural memories" comment — any syncFromDisk() call can delete reflection-generated skills from SwiftData.
- **D-3 [MEDIUM-LOW] Un-refreshed cache reads inside RoutineManager itself:** dispatchReaction, startScheduledRoutines, exportRoutinesSummaryAsMarkdown all read `routines` with no loadRoutines(). Safe-but-stale in daemon mode; the destroyed-instance trap returns if the context is ever repointed.
- **D-4 [LOW] reset() does not stop the scheduler:** TickerScheduler registration ("RoutineManager.heartbeat") is only removed by stopScheduledRoutines(); reset() invalidates cronHeartbeatTimer, which is never assigned anywhere (dead legacy timer). recentRuns also survives reset().
- **D-5 [LOW] rateLimiters grows unboundedly** (one TokenBucket per client IP, no cap/TTL eviction).
- **D-6 [LOW] Routine-run history decode is strict:** loadRuns() bare-decodes runs.json; any schema mismatch discards the whole history instead of using the existing ResilientJSONStore pattern.
- **D-7 [LOW] ApexGatewayClient has no frame cap:** readNextMessage trusts an unchecked UInt32 length (server caps at 8 MiB; client doesn't) — a malicious/buggy server can force a huge allocation attempt.
- **D-8 [INFO] Silent persistence failures:** RoutineManager save/delete/toggle use `try? context.save()` — a failed SwiftData save is invisible except via subsequent loadRoutines() state.

## 4. Prioritized fix list

1. **Wire the confirmation gate to the risk map** (C-1): make shouldConfirmTool return true for AgentSecurity .high tools (keep the denied-tools kill-switch and requireConfirmationForAll semantics). Add a test that fails if any .high tool is ungated. This single change closes most of the remaining confirmation exposure.
2. **Close the nested-confirmation leak completely** (Area-2 #1 + C-5): extend the TaskLocal scoping from executeToolByName to the executeWithLogging path so depth is per-tool-frame, and make the confirmationPerformed setter idempotent.
